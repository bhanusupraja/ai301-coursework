# Rubric: is this plan ready to post and build from?

Read the whole package (issue context, repo facts, repro evidence, plan, plan comment) before grading. Every check judges the thing itself against the issue and its repro evidence, never the write-up's length, headings or polish. A terse plan can be ready; a long confident one can be wrong.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause, read against every step, control run and artifact in the repro-evidence block (not only the "Actual" summary). | The stated cause is consistent with all of the repro evidence, including the control runs, and explains the symptom the repro shows. Fail if any control, step or artifact in the repro evidence rules the stated cause out (for example a control where the blamed component works fine, or an artifact showing the bad value already exists before the blamed step), if the plan blames a different component than the evidence isolates, or if the plan states no cause at all and proposes to find it during the build. Adopting a diagnosis from the issue thread does not make it grounded: check it against the repro artifacts. | required |
| scope-bounded | The plan's in-scope and not-in-scope statements and its approach steps, read against the one symptom the issue and repro evidence describe. | The plan is one bounded change that fixes the reproduced symptom, and every approach step is needed for that. Fail if the plan bundles work the symptom does not need: a rewrite, migration, redesign, new option or setting, new framework, refactor of neighbouring code, or "while I'm in the area" extras, even when the core fix inside it is right. A not-in-scope line that explicitly defers a larger rework with a reason is good scope, not creep. A deliberately scoped-down fix passes if it says what it leaves out. | required |
| stranger-can-start | The plan's files or areas, chosen approach and order of steps. | A stranger could begin editing without asking the author anything: the plan names the file(s) or code area to change and commits to one approach. Fail if a decision the build depends on is left open ("somewhere", "whichever is easier", "gocui or tcell, not sure", "investigate first", "profile and optimize"), if no file or area is named, or if the approach is a direction rather than a change. A small, named, stated unknown that does not block starting (a risk to check mid-build) does not fail. | required |
| test-observable | The plan's test plan, read against the repro-evidence steps and expected result. | The test plan names an outcome someone can observe that shows this fix worked: it re-runs the repro (or its inputs) and states what output, value, exit code or behaviour must change from the "Actual" in the repro evidence. Fail if the test plan is only "run the full test suite", "make sure nothing else breaks", "should feel fast", a manual look with no stated expected result, or otherwise would pass whether or not the bug was fixed. | required |
| honest-uncertainty | The plan's and the comment's confidence words and risk or open-question statements, set against what the repro evidence actually shows. | The plan and the comment claim only what the repro evidence supports; where the fix leaves a real risk or open question (a performance cost, another affected path, an untestable variant) it is said, not hidden. Fail if the plan or comment asserts as fact something the repro evidence does not show, guarantees results ("this will fix all", "guaranteed", "no risk") or hides an open question the thread or repro evidence raises. A short plan with no stated risk passes when nothing it claims goes beyond the evidence. | required |
| thread-aware | The plan comment, read against the "Thread highlights" of the issue (maintainer and collaborator comments, prior PRs, rejected approaches, requests for testing). | If a maintainer or collaborator in the thread gave explicit direction (chose or rejected an approach, isolated a culprit file, asked for something to be tested, pointed to an open PR), the comment engages it: it follows that direction, or says why it differs, and does not race or ignore an existing PR. If the thread has no such direction, pass. Fail if the plan contradicts or sidesteps the maintainer's stated direction without saying so. | required |
| repo-conventions | The repo-facts block (bug-report template asks, contribution policy including any AI-use rule) against the wording of the plan comment. | If the repo's stated policy requires disclosing AI assistance, the comment contains an explicit disclosure (tool and extent as the policy asks); course packages are treated as AI-assisted work. If the policy is silent, permissive, or has no disclosure requirement, pass. A rule that comments must be in the author's own words is not a disclosure requirement: pass if the comment reads as plain human voice. Fail only if a disclosure requirement exists and the comment does not comply. | required |

## Verdict rule

Accept if every check above passes. There are no preferred checks. A check graded unclear counts as fail: a plan that cannot be verified from the package is not ready to build from. Reject otherwise. Quote the failed check's deciding evidence in the output.
