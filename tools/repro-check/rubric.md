# Rubric: is this reproduction package ready to post?

Read the whole package (issue context, repo facts, claim comment, repro report) before grading. Every check judges the thing itself against the issue, never the write-up's length, headings or polish.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment line(s), read against the repo-facts block and the issue's stated target. | The report names the tool/program version AND the OS or platform, plus any setting the issue's failure depends on (driver, shell, build profile, backend). A reader could place the attempt on the same footing as the issue. Fail if any of these is absent, or the whole record is missing. | required |
| steps-rerunnable | The commands, config and inputs in the repro report, from starting state to trigger. | A stranger could run them as written: exact commands or config text are shown, nothing depends on a private repo, private config or unnamed setup, and the trigger input is included. The trigger input may live in the issue: if the issue body gives it verbatim and the report points to it exactly (for example "the issue's two calls with the issue's ranges"), or a small file is described precisely enough to rebuild with the trigger element named (for example "a valid dependencies list plus a `category:` section"), that counts as included. Fail if a step says only "set up the project", the trigger element is unnamed, or it relies on resources a stranger cannot get. | required |
| behavior-matches-issue | The output excerpts/logs in the repro report, compared line by line with the symptom the issue quotes (error text, exit code, wrong output, crash vs. graceful error). Also compare the trigger input with the issue's own. | The artifact itself shows the issue's specific symptom, produced by the issue's trigger (same syntax, same operator, same input shape). An honest cannot-reproduce passes this check when it ran the issue's own trigger, or a good-faith attempt to produce it whose shortfall (what it could not force or match) is stated openly, never swapping in a different symptom, and shows the real outcome of that run; it cannot be expected to show a symptom it did not see, but it must not claim one. Fail if the artifact shows an adjacent symptom (a graceful validation error instead of a crash, garbled output instead of a crash, a compile error instead of the runtime error), if the input was altered so a different thing fails, or if the artifacts only show the tool runs and nothing shows the bug. | required |
| target-faithful | The report's environment versions against the issue's confirmed versions and the repo-facts latest release. | The version/platform tested matches what the issue reports or the current release, OR any deviation is stated openly in the report and the conclusions stay inside what was tested. Fail if an old or different version is used silently, or if the result is generalized to a platform/release that was not tested. | required |
| honest-outcome | Each claim sentence in the claim comment and report ("confirmed", "verified", "ran it N times", "the cause is X") against the artifacts shown. | Every claim is backed by something shown in the package. An honest cannot-reproduce passes if it shows a real attempt, the artifacts, and what differed. Fail if a load-bearing claim has no artifact behind it: confirmation with no artifacts, a root cause stated with no shown evidence, counts or certainty with nothing behind them, or an artifact that contradicts the sentence next to it. A minor secondary observation (such as a one-line control result) stated plainly, consistent with the shown artifacts and the issue thread, and not carrying the conclusion, does not fail. In a cannot-reproduce, a repeat-run count or a variant attempt that is described alongside a shown representative run and whose outcome matches that run is not a fail, and a clearly hedged hypothesis about why it did not reproduce ("may", "appears", "might need") is a stated guess, not a claim; fail only if the hypothesis is asserted as fact, or the report claims the bug. | required |
| claim-specific-modest | The claim comment, read against the issue title and body. | The claim names details of this issue (the symptom, a file, a command, a version) and a concrete next step, and promises only investigation or a report. Fail if it could be pasted onto any issue (boilerplate "assign me"), is only a +1 or me-too, or promises a fix, a guarantee or a deadline. | required |
| repo-conventions | The repo-facts block (bug-report template asks, contribution policy including AI-use rules) against the wording of both comments. | If the repo's stated policy requires disclosing AI assistance, both comments contain an explicit disclosure (tool and extent as the policy asks); course packages are treated as AI-assisted work. If the policy is silent, permissive, or has no disclosure requirement, pass. A rule that comments must be human-written or in the author's own words is not a disclosure requirement: pass if the comments read as plain human voice, and fail only if the policy asks for AI use to be disclosed (or forbids it) and the comments do not comply. Fail if a disclosure requirement exists and the comments do not disclose it. | required |
| control-run | The repro report. | The report includes a control or contrast run (a variant that does not trigger, or a different config) that narrows the trigger. | preferred |

## Verdict rule

Accept if every required check passes. Preferred checks never change the verdict. A required check graded unclear counts as fail: proof that cannot be verified is not ready to post. Reject otherwise.
